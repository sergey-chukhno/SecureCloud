# 1. Global Data Modeling Rules and Identifier Strategy

## 1.1 Purpose

This document defines the concrete persistence model of SecureCloud.

It specifies:

* data ownership;
* identifiers;
* entity relationships;
* storage responsibilities;
* primary access patterns;
* database keys and partitions;
* lifecycle and deletion rules.

The model follows the approved service architecture:

| Service   | Primary persistence |
| --------- | ------------------- |
| Auth      | PostgreSQL          |
| Messaging | ScyllaDB            |
| Files     | PostgreSQL + MinIO  |
| Audit     | ClickHouse          |

The Gateway owns no persistent business data.

---

## 1.2 Service-Owned Data

Each runtime service exclusively owns its persistent data.

A service:

* defines its schema;
* performs reads and writes to its storage;
* exposes data to other services through APIs;
* does not allow other services to query its database directly.

The ownership model is:

```text
Auth
 └── PostgreSQL
      ├── users
      ├── devices
      ├── device public keys
      ├── sessions
      ├── refresh tokens
      └── MFA configuration

Messaging
 └── ScyllaDB
      ├── conversations
      ├── memberships
      ├── messages
      ├── delivery state
      ├── read state
      └── synchronization state

Files
 ├── PostgreSQL
 │    ├── file metadata
 │    └── upload state
 │
 └── MinIO
      └── encrypted binary objects

Audit
 └── ClickHouse
      └── immutable audit events
```

Cross-service relationships are represented using opaque identifiers rather than database foreign keys.

For example:

```text
Messaging.conversation_participant.user_id
```

references a user owned by Auth, but Messaging does not create a PostgreSQL foreign key into Auth's database.

---

## 1.3 Opaque Identifier Strategy

SecureCloud uses globally unique opaque identifiers.

The following identifier types are canonical:

```text
UserId
DeviceId
ConversationId
MessageId
FileId
SessionId
RefreshTokenId
MfaConfigurationId
MfaChallengeId
AuditEventId
RequestId
CorrelationId
IdempotencyKey
UploadId
```

Identifiers must not expose:

* human identity;
* email address;
* device name;
* database sequence numbers;
* infrastructure topology;
* creation volume.

---

## 1.4 Identifier Format

All persistent domain identifiers use **UUIDv7**.

Examples:

```text
UserId         UUIDv7
DeviceId       UUIDv7
ConversationId UUIDv7
MessageId      UUIDv7
FileId         UUIDv7
SessionId      UUIDv7
AuditEventId   UUIDv7
UploadId       UUIDv7
```

UUIDv7 is selected because it provides:

* global uniqueness;
* opaque identifiers;
* approximately time-ordered generation;
* efficient ordering compared with fully random identifiers;
* no central identifier generator.

UUIDv7 identifiers are generated by the service creating the corresponding entity.

The identifier is never reassigned.

---

## 1.5 Identifier Ownership

The service creating an entity owns its identifier.

| Entity       | Identifier       | Owner                                |
| ------------ | ---------------- | ------------------------------------ |
| User         | `UserId`         | Auth                                 |
| Device       | `DeviceId`       | Auth                                 |
| Conversation | `ConversationId` | Messaging                            |
| Message      | `MessageId`      | Messaging                            |
| File         | `FileId`         | Files                                |
| Upload       | `UploadId`       | Files                                |
| Session      | `SessionId`      | Auth                                 |
| Audit event  | `AuditEventId`   | Event producer                       |
| Request      | `RequestId`      | Gateway                              |
| Correlation  | `CorrelationId`  | Request initiator/orchestrating flow |

An identifier remains valid as a reference even when the underlying entity becomes inactive or deleted according to its lifecycle policy.

For example, a revoked `DeviceId` remains historically meaningful.

---

## 1.6 Cross-Service References

Cross-service references are opaque.

For example:

```text
Messaging
    │
    ├── user_id   ─────► Auth UserId
    │
    └── device_id ─────► Auth DeviceId
```

Messaging stores the identifiers required for its domain but does not duplicate Auth's complete user record.

Similarly:

```text
Files
   │
   ├── owner_user_id ───► Auth UserId
   │
   └── conversation_id ─► Messaging ConversationId
```

Audit stores references to resources but does not own those resources.

---

## 1.7 Referential Consistency Across Services

Cross-service referential integrity is enforced at the application/API level.

There are no distributed database foreign keys.

For example, before Messaging accepts an operation requiring a valid device, the service relies on the authenticated request context and relevant Auth/device validation rules.

Messaging must not directly query Auth's PostgreSQL database.

A historical record may continue to reference:

```text
UserId
DeviceId
ConversationId
```

even if the corresponding entity is later deactivated.

Historical references must not be rewritten merely because an entity changes state.

---

## 1.8 Timestamps

Persistent records use explicit UTC timestamps.

The canonical format is:

```text
timestamp with time zone
```

for PostgreSQL and equivalent UTC timestamp types for other persistence technologies.

Where relevant, entities use:

```text
created_at
updated_at
```

Additional domain timestamps are used when required:

```text
revoked_at
expires_at
deleted_at
delivered_at
read_at
accepted_at
completed_at
```

Timestamps represent distinct events and must not be overloaded.

For example:

```text
created_at   ≠ delivered_at
created_at   ≠ read_at
revoked_at   ≠ deleted_at
```

---

## 1.9 Time Source

Services use synchronized system clocks.

All persisted timestamps are stored in UTC.

Services must not use client-provided timestamps as authoritative server timestamps for:

* authentication;
* device revocation;
* session expiration;
* audit ingestion;
* message acceptance.

Client-provided timestamps may be stored as application metadata where required, but are distinguished from server-observed timestamps.

---

## 1.10 Entity State

Entities use explicit state where lifecycle matters.

Examples:

```text
Device
 ├── ACTIVE
 └── REVOKED

Session
 ├── ACTIVE
 ├── REVOKED
 └── EXPIRED

RefreshToken
 ├── ACTIVE
 ├── ROTATED
 ├── REVOKED
 └── EXPIRED

Upload
 ├── CREATED
 ├── IN_PROGRESS
 ├── COMPLETED
 ├── FAILED
 └── EXPIRED
```

State transitions are explicit domain operations.

The implementation must not infer state solely from nullable timestamps where a meaningful lifecycle exists.

---

## 1.11 Optimistic Versioning

Mutable relational entities that may be modified concurrently use an integer version where optimistic concurrency control is required.

Conceptually:

```text
version = 1
```

A state update becomes:

```text
UPDATE entity
SET ...
    version = version + 1
WHERE id = :id
  AND version = :expected_version
```

This is used selectively.

It is not added to immutable or append-only records without a concurrency requirement.

---

## 1.12 Sensitive Data Classification

Persistent data is classified into three practical categories.

### Authentication secrets

Examples:

* password verifier;
* refresh-token verifier;
* MFA secret material.

These require dedicated protection and are never returned through normal APIs.

### Public cryptographic material

Examples:

* identity public keys;
* device public keys;
* signed public-key metadata.

These may be distributed to other authorized users/devices according to Auth's directory rules.

### Application ciphertext

Examples:

* encrypted message envelopes;
* encrypted file objects.

Backend services may persist and route these values without possessing the plaintext.

---

## 1.13 Private Key Rule

SecureCloud server-side persistence must never contain user/device E2E private keys.

Specifically, Auth does not store:

* identity private keys;
* device private keys;
* message private keys;
* ratchet private state;
* plaintext file-encryption keys.

These remain client-side cryptographic material.

A stolen Auth database must therefore not provide an attacker with the private E2E identities required to decrypt SecureCloud communications.

---

## 1.14 Public-Key Versioning

Public cryptographic material is versioned rather than overwritten without history.

A device key record therefore has:

```text
key_id
device_id
key_type
public_key
created_at
revoked_at
status
```

A key change creates a new version/record.

Historical messages can continue referencing the cryptographic key identity used when the message was created.

---

## 1.15 Deletion

Deletion behavior depends on the domain.

SecureCloud does not apply a single universal deletion strategy.

Examples:

| Domain                   | Default strategy                           |
| ------------------------ | ------------------------------------------ |
| Device                   | State transition to `REVOKED`              |
| Session                  | State transition + expiration              |
| Refresh token            | Revocation/expiration                      |
| Cryptographic public key | Historical record retained, status changed |
| Message                  | Domain retention policy                    |
| File                     | Lifecycle-based deletion                   |
| Audit event              | Retention/TTL policy                       |

Historical security records must not be silently rewritten.

---

## 1.16 Data Serialization

Service APIs define canonical external/internal representations.

Persistence schemas remain implementation details of the owning service.

Identifiers are transported as explicit typed UUID values where supported.

Internal service communication uses Protocol Buffers.

External REST APIs use JSON representations.

A database schema must not become the public API contract.
