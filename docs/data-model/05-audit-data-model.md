# 5. Audit Service Data Model

## 5.1 Purpose and Ownership

The Audit Service owns the SecureCloud application-level security and audit trail.

It records security-relevant and operationally significant events produced by SecureCloud runtime services.

The Audit Service does not own the business data of any other service.

It does not own:

* users;
* credentials;
* MFA configurations or secrets;
* conversations;
* groups;
* messages;
* encrypted message payloads;
* files;
* encrypted file content;
* file metadata;
* delivery state;
* runtime infrastructure state.

The Audit Service owns only audit records.

---

## 5.2 Runtime Event Producers

The Audit Service receives audit events from SecureCloud runtime services:

```text
Gateway
Auth Service
Messaging Service
Files Service
```

The corrected ownership model is:

```text
Gateway ────────────┐
                    │
Auth Service ───────┤
                    │
Messaging Service ──┼────► Audit Service ─────► ClickHouse
                    │
Files Service ──────┘
```

The Audit Service itself may also record internal Audit Service events when required, for example:

```text
audit.event.rejected
audit.producer.authentication.failed
```

These events are generated by the Audit Service and stored in its own event store.

---

## 5.3 Infrastructure Is Not an Audit Event Producer

Infrastructure and deployment components are not runtime producers in the SecureCloud Audit Service model.

The following are outside the Audit Service domain:

```text
Docker Compose
Kubernetes
CI/CD pipelines
Deployment tooling
Database infrastructure
Object storage infrastructure
Container runtime logs
Infrastructure metrics
Infrastructure traces
```

These components use infrastructure logging and observability mechanisms.

Therefore:

> SecureCloud Audit Service ≠ infrastructure logging system.

The Audit Service records application-level audit events.

Infrastructure observability remains part of the infrastructure/control plane.

---

## 5.4 Persistence Technology

The Audit Service persistence technology is:

> **ClickHouse**

ClickHouse is the authoritative audit event store.

The Audit Service owns the ClickHouse database/schema used for audit data.

No other runtime service directly writes to the Audit Service tables.

The persistence model is:

```text
Runtime Service
      │
      │ authenticated audit event
      ▼
Audit Service
      │
      │ validated batch insert
      ▼
ClickHouse
```

ClickHouse is selected because the Audit workload is:

* append-heavy;
* high-volume;
* time-oriented;
* analytical;
* primarily read by filtering and aggregation;
* not dependent on relational joins.

---

# 5.5 Audit Event Model

Every audit event contains a common canonical set of fields.

The logical model is:

```text
AuditEvent
├── event_id
├── occurred_at
├── received_at
├── event_type
├── severity
├── producer_service
├── producer_instance
├── actor_type
├── actor_id
├── target_type
├── target_id
├── correlation_id
├── causation_id
└── event_data
```

---

## 5.6 Event Identity

Every event receives:

```text
event_id UUID
```

The producing runtime service generates the identifier.

For SecureCloud:

> **UUIDv7 is used for audit event identifiers.**

The identifier provides:

* global uniqueness;
* distributed generation;
* time-ordering characteristics;
* efficient chronological behavior.

`event_id` is also the logical idempotency identifier.

A producer retrying the same audit event must reuse the same `event_id`.

---

# 5.7 Event Time

Every audit event stores two timestamps.

## `occurred_at`

The time at which the event occurred in the producing service.

Example:

```text
Authentication failed:
2026-09-08 14:02:10.123 UTC
```

---

## `received_at`

The time at which the Audit Service accepted the event.

Example:

```text
Audit Service received event:
2026-09-08 14:02:10.847 UTC
```

These timestamps are intentionally different.

The Audit Service preserves both values.

```text
occurred_at = business/security event time

received_at = Audit Service ingestion time
```

---

# 5.8 Event Type

`event_type` identifies what happened.

The MVP uses canonical hierarchical string values.

Examples:

```text
gateway.request.rejected
gateway.rate_limit.exceeded

auth.login.succeeded
auth.login.failed
auth.logout

auth.mfa.challenge.created
auth.mfa.challenge.succeeded
auth.mfa.challenge.failed

device.registered
device.revoked

security.token.rejected
security.authorization.denied
security.service.authentication.failed

conversation.created
conversation.membership.changed

message.submitted
message.delivery.failed

file.upload.completed
file.available
file.deleted

emergency.activated
emergency.action.executed
```

Event types are part of the internal Audit Service contract.

They must not be renamed without explicitly updating producers and consumers.

---

# 5.9 Severity

Every event has one severity:

```text
INFO
WARNING
SECURITY
CRITICAL
```

Meaning:

### INFO

Normal security-relevant lifecycle activity.

Examples:

* successful authentication;
* successful MFA;
* device registration.

### WARNING

Unexpected or suspicious activity.

Examples:

* repeated failed authentication;
* unusual authentication behavior.

### SECURITY

A security control rejected or blocked an action.

Examples:

* invalid token;
* authorization denied;
* revoked device access attempt.

### CRITICAL

High-priority security or emergency event.

Examples:

* emergency activation;
* critical identity compromise signal.

---

# 5.10 Producer

Every event identifies the runtime service that produced it.

```text
producer_service
producer_instance
```

Examples:

```text
producer_service = AUTH
producer_instance = auth-2
```

or:

```text
producer_service = MESSAGING
producer_instance = messaging-4
```

`producer_service` identifies the logical runtime service.

`producer_instance` is optional operational metadata identifying the specific service instance.

The producer authenticates to the Audit Service using the service-to-service authentication architecture defined by ADR-008.

Unauthenticated producers cannot submit audit events.

---

# 5.11 Actor

The actor represents the entity that initiated or performed an action.

The canonical fields are:

```text
actor_type
actor_id
```

Actor types include:

```text
USER
DEVICE
SERVICE
SYSTEM
UNKNOWN
```

Examples:

```text
actor_type = USER
actor_id = User UUID
```

or:

```text
actor_type = DEVICE
actor_id = Device UUID
```

or:

```text
actor_type = SERVICE
actor_id = AUTH
```

The Audit Service stores opaque identifiers.

It does not duplicate user profile information.

---

# 5.12 Target

The target represents the entity affected by an action.

The canonical fields are:

```text
target_type
target_id
```

Examples:

```text
target_type = DEVICE
target_id = Device UUID
```

for:

```text
User revoked Device X
```

or:

```text
target_type = FILE
target_id = File UUID
```

for:

```text
File X was deleted
```

Supported target types initially include:

```text
USER
DEVICE
CONVERSATION
FILE
SERVICE
```

Additional target types may be added when new domain entities require auditing.

The Audit Service does not enforce foreign keys to other services.

`target_id` remains an opaque identifier owned by the corresponding domain service.

---

# 5.13 Correlation and Causation

The Audit model supports distributed operation reconstruction.

Every event may contain:

```text
correlation_id
causation_id
```

## Correlation ID

`correlation_id` identifies one larger distributed operation.

Example:

```text
Client request
      │
      ▼
Gateway
      │
      ▼
Auth
      │
      ▼
Messaging
```

All related audit events can share:

```text
correlation_id
```

This allows investigation across service boundaries.

---

## Causation ID

`causation_id` optionally identifies the immediately preceding event.

Example:

```text
Event A
Login Attempt

        │

        ▼

Event B
MFA Challenge
causation_id = Event A
```

`causation_id` is optional.

It is used when one event directly caused another event.

---

# 5.14 Event Data

`event_data` stores bounded event-specific metadata.

Examples:

```json
{
  "failure_reason": "INVALID_CREDENTIALS"
}
```

or:

```json
{
  "reason": "USER_REQUESTED"
}
```

The data is stored as:

```text
event_data String
```

containing JSON.

The Audit Service treats this data as audit metadata.

It must remain bounded.

The following data must never be stored:

* passwords;
* password hashes;
* access tokens;
* refresh tokens;
* MFA secrets;
* private keys;
* plaintext messages;
* decrypted message payloads;
* plaintext files;
* decrypted file content.

The Audit Service records security facts, not secrets or application content.

---

# 5.15 ClickHouse Table

The MVP Audit Service uses the following primary table.

```sql
CREATE TABLE audit_events
(
    event_id UUID,

    occurred_at DateTime64(3, 'UTC'),
    received_at DateTime64(3, 'UTC'),

    event_type LowCardinality(String),
    severity LowCardinality(String),

    producer_service LowCardinality(String),
    producer_instance String,

    actor_type LowCardinality(String),
    actor_id String,

    target_type LowCardinality(String),
    target_id String,

    correlation_id UUID,
    causation_id UUID,

    event_data String
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(occurred_at)
ORDER BY
(
    occurred_at,
    producer_service,
    event_type,
    event_id
);
```

The table is append-oriented.

The application does not perform normal business updates on audit events.

---

# 5.16 Why MergeTree

The selected engine is:

> **MergeTree**

This is appropriate because the audit workload consists primarily of:

```text
INSERT events
      +
time-range queries
      +
filtered investigations
      +
analytical queries
```

Audit events are immutable after insertion.

MergeTree matches this workload.

---

# 5.17 Partitioning Strategy

The concrete partitioning strategy is:

```sql
PARTITION BY toYYYYMM(occurred_at)
```

Therefore, events are partitioned by month.

Example:

```text
2026-09
2026-10
2026-11
```

Monthly partitioning provides a practical balance between:

* partition count;
* retention management;
* time-range queries;
* high-volume ingestion.

The Audit Service does not create one partition per day.

For the expected MVP scale, daily partitions would create unnecessary partition management overhead.

---

# 5.18 Ordering Key

The concrete ordering key is:

```sql
ORDER BY
(
    occurred_at,
    producer_service,
    event_type,
    event_id
)
```

The primary expected audit access pattern is chronological investigation.

Therefore:

```text
occurred_at
```

is the first ordering component.

The remaining fields provide useful locality for common investigation filters.

The final identifier:

```text
event_id
```

ensures deterministic ordering between events that share the same preceding ordering values.

---

# 5.19 Query Patterns

The Audit Service is optimized for the following queries.

## Time range

```sql
SELECT *
FROM audit_events
WHERE occurred_at >= ?
  AND occurred_at < ?;
```

---

## Producer investigation

```sql
SELECT *
FROM audit_events
WHERE producer_service = ?
  AND occurred_at >= ?
  AND occurred_at < ?;
```

---

## Event type investigation

```sql
SELECT *
FROM audit_events
WHERE event_type = ?
  AND occurred_at >= ?
  AND occurred_at < ?;
```

---

## Severity investigation

```sql
SELECT *
FROM audit_events
WHERE severity IN ('SECURITY', 'CRITICAL')
  AND occurred_at >= ?
  AND occurred_at < ?;
```

---

## Actor investigation

```sql
SELECT *
FROM audit_events
WHERE actor_type = ?
  AND actor_id = ?
  AND occurred_at >= ?
  AND occurred_at < ?;
```

---

## Target investigation

```sql
SELECT *
FROM audit_events
WHERE target_type = ?
  AND target_id = ?
  AND occurred_at >= ?
  AND occurred_at < ?;
```

---

## Correlation investigation

```sql
SELECT *
FROM audit_events
WHERE correlation_id = ?;
```

The correlation query may scan more data than time-oriented queries because `correlation_id` is not the leading ordering key.

For the MVP, this is acceptable.

If correlation queries become a demonstrated hot path, a dedicated ClickHouse projection or secondary data-skipping strategy may be introduced based on actual requirements.

No additional index structure is introduced prematurely.

---

# 5.20 Ingestion Strategy

Audit events are ingested asynchronously.

The normal flow is:

```text
Runtime Service
      │
      │ Business operation
      ▼
Runtime Service database transaction
      │
      ├── Domain state change
      │
      └── Audit event written to Outbox
                │
                ▼
         Outbox Publisher
                │
                ▼
           Audit Service
                │
                ▼
       Validate producer identity
                │
                ▼
       Validate event schema
                │
                ▼
          Batch events
                │
                ▼
       INSERT INTO ClickHouse
```

The Audit Service does not become part of the synchronous critical path of normal Messaging, Files, or Auth operations.

---

# 5.21 Batch Ingestion

The Audit Service batches validated events before inserting them into ClickHouse.

The concrete MVP strategy is:

```text
Maximum batch size:
1,000 events

Maximum batching delay:
100 milliseconds
```

An insert is performed when either limit is reached.

```text
1,000 events
       OR
100 ms elapsed
       │
       ▼
ClickHouse INSERT
```

This provides efficient ClickHouse ingestion while keeping audit-event ingestion latency bounded.

---

# 5.22 Ingestion Concurrency

The Audit Service uses a bounded ingestion pipeline.

The concrete MVP model is:

```text
Authenticated Producers
        │
        ▼
Bounded Ingestion Queue
        │
        ▼
Validation Workers
        │
        ▼
Batch Builder
        │
        ▼
Bounded Insert Workers
        │
        ▼
ClickHouse
```

The service does not create one unbounded queue per producer.

The queue is globally bounded.

The number of validation and insertion workers is configurable according to deployment resources.

For the MVP, the initial deployment configuration is:

```text
Validation workers:
4

Insert workers:
2

Maximum in-memory queued events:
10,000
```

When the queue is full, the Audit Service applies backpressure to producers.

It does not silently discard security audit events.

---

# 5.23 Backpressure

If the Audit Service is temporarily unable to ingest events fast enough:

```text
Runtime Service
      │
      ▼
Outbox remains durable
      │
      ▼
Publisher retries later
```

The runtime service's durable outbox is the primary protection against temporary Audit Service or ClickHouse unavailability.

The Audit Service does not require an unbounded in-memory buffer.

---

# 5.24 Deduplication and Idempotency

Audit event delivery is:

> **At-least-once**

A producer may resend an event because:

* an acknowledgement was lost;
* the network failed;
* the publisher restarted;
* the Audit Service restarted.

Therefore, duplicate delivery is possible.

The producer must resend the same:

```text
event_id
```

for the same logical event.

The Audit Service maintains a short-lived in-memory deduplication cache for recently accepted `event_id` values.

The concrete MVP configuration is:

```text
Deduplication cache:
100,000 recent event IDs

TTL:
10 minutes
```

This prevents the most common retry duplicates.

ClickHouse remains an append-oriented analytical store and is not treated as a traditional transactional unique-constraint database.

Therefore:

> **The system provides application-level idempotency for normal retries rather than relying on a ClickHouse UNIQUE constraint.**

Longer-term duplicates outside the cache window are detectable by `event_id` during analytical investigation.

---

# 5.25 Duplicate Detection Query

Potential duplicates can be detected with:

```sql
SELECT
    event_id,
    count() AS occurrences
FROM audit_events
GROUP BY event_id
HAVING occurrences > 1;
```

This query is an operational verification mechanism.

It is not part of the normal ingestion path.

---

# 5.26 Immutability

Audit events are immutable.

The Audit Service does not expose operations equivalent to:

```text
UpdateAuditEvent
DeleteAuditEvent
```

The normal persistence operation is:

```text
INSERT audit event
```

If something changes later, the system creates another event.

Example:

```text
device.registered
```

followed later by:

```text
device.revoked
```

The historical registration event remains unchanged.

---

# 5.27 Retention and TTL

The Audit Service uses time-based retention.

The initial data model defines:

> **36 months of audit event retention**

The concrete ClickHouse policy is:

```sql
TTL occurred_at + INTERVAL 36 MONTH
```

Therefore:

```text
Event occurs
      │
      ▼
Stored in ClickHouse
      │
      ▼
Retained for 36 months
      │
      ▼
Eligible for automatic removal
```

The 36-month period is the concrete MVP default.

It can later be changed for specific deployments where legal or customer requirements differ.

The full table definition therefore includes:

```sql
TTL occurred_at + INTERVAL 36 MONTH
```

# 5.29 Sensitive Data Invariants

The following must never enter the Audit Service:

```text
Passwords
Password hashes
Access tokens
Refresh tokens
JWT values
MFA secrets
Private keys
Session keys
Plaintext messages
Decrypted message payloads
Plaintext file content
Decrypted file content
```

The Audit Service records:

```text
who acted
what happened
what was affected
when it happened
which service produced the event
the security result
bounded event-specific metadata
```

It does not store application secrets or communication content.

---

# 5.30 Cryptographic Integrity — Future Checkpoints

The MVP does not implement per-event cryptographic hash chains.

The MVP relies on:

* append-only application semantics;
* authenticated service producers;
* controlled database access;
* durable producer outboxes;
* backup and recovery procedures;
* immutable historical event semantics.

A future enhancement may introduce periodic cryptographic checkpoints.

The conceptual model is:

```text
Audit events for time period
           │
           ▼
Canonical cryptographic digest
           │
           ▼
Cryptographically signed checkpoint
```

A checkpoint could contain:

```text
checkpoint_id
period_start
period_end
event_count
events_digest
created_at
signature
```

Checkpoint verification would allow the system to detect modification of historical event data.

This feature is explicitly deferred from the MVP.

# 5.32 Section Summary

The SecureCloud Audit Service uses ClickHouse as an append-oriented analytical audit store.

```text
Gateway ────────────┐
                    │
Auth ───────────────┤
                    │
Messaging ──────────┼────► Audit Service
                    │             │
Files ──────────────┘             ▼
                             ClickHouse
```

The concrete design provides:

* runtime-service-only audit producers;
* clear separation from infrastructure observability;
* UUIDv7 event identities;
* immutable append-only audit records;
* monthly ClickHouse partitions;
* chronological ordering;
* bounded asynchronous ingestion;
* batch inserts;
* durable producer outboxes;
* application-level retry deduplication;
* explicit query patterns;
* 36-month TTL retention;
* strict sensitive-data exclusion;
* future optional cryptographic checkpoints without introducing unnecessary MVP coordination complexity.
