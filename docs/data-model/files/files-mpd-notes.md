1. files

files is the authoritative PostgreSQL table for the logical file and its lifecycle.

Primary key
PRIMARY KEY (file_id)

file_id is the canonical SecureCloud FileId, generated by the Files Service. The approved MVP identifier format is UUIDv7.

Physical model
files
├── file_id
├── lifecycle_state
├── encrypted_size_bytes
├── chunk_count
├── encryption_version
├── ciphertext_integrity_hash
├── created_at
├── available_at
├── expires_at
├── deleted_at
└── metadata_version
Important constraints

The table intentionally does not store:

original_filename
plaintext_mime_type
original_size_bytes
object_key
plaintext_file_content

Human-readable metadata remains inside encrypted application metadata, while the backend stores only the operational metadata necessary to manage the encrypted file.

Lifecycle
UPLOAD_CREATED
       ↓
UPLOADING
       ↓
AVAILABLE
     ↙       ↘
EXPIRED     DELETED

Only AVAILABLE files may be downloaded. PostgreSQL lifecycle state remains authoritative even if an encrypted object happens to exist in object storage.

2. upload_sessions

upload_sessions stores durable state for resumable uploads.

Primary key
PRIMARY KEY (upload_id)
Relationship
upload_sessions.file_id
    → files.file_id

Each upload session belongs to one file.

The approved MVP decision is:

One active upload session per file.

Physical model
upload_sessions
├── upload_id
├── file_id
├── lifecycle_state
├── expected_chunk_count
├── encrypted_size_bytes
├── created_at
├── updated_at
└── expires_at

This state survives:

client disconnect;
Gateway restart;
Files Service restart;
network interruption.

Upload progress itself is represented through upload_chunks.

3. upload_chunks

upload_chunks represents completed encrypted chunks belonging to an upload session.

Composite primary key
PRIMARY KEY (
    upload_id,
    chunk_index
)

The identity of a logical chunk upload is therefore:

UploadId + ChunkIndex
Physical model
upload_chunks
├── upload_id
├── chunk_index
├── encrypted_chunk_size
├── chunk_integrity_hash
└── uploaded_at

The table provides durable upload progress.

For example:

Upload U100

Chunk 0 ✓
Chunk 1 ✓
Chunk 2 ✓
Chunk 3 ✗
Chunk 4 ✓
Chunk 5 ✗

After reconnection, the service can determine which chunks already completed and the client uploads only the missing chunks.

Integrity constraint

The same (upload_id, chunk_index) cannot represent two different encrypted chunks.

On retry:

existing chunk hash
        =
retried chunk hash

→ retry is accepted idempotently.

If the hashes differ:

existing chunk hash
        ≠
retried chunk hash

→ upload is rejected as inconsistent.

4. outbox_events

outbox_events implements the Files Service Transactional Outbox.

Primary key
PRIMARY KEY (event_id)
Physical model
outbox_events
├── event_id
├── aggregate_type
├── aggregate_id
├── event_type
├── payload
├── created_at
├── published_at
└── publication_status

For Files Service events:

aggregate_type = FILE
aggregate_id   = FileId

The outbox provides atomicity between:

PostgreSQL domain state
        +
domain event creation

The most important example is:

files.lifecycle_state = AVAILABLE
        +
FILE_AVAILABLE event

Both changes occur inside the same PostgreSQL transaction.

The publisher runs afterward; synchronous event publication is not required for the lifecycle transaction to commit.

5. External encrypted object storage

This is part of the Files Service physical persistence architecture but is not a relational table.

FileId
   ↓
deterministic derivation
   ↓
files/{FileId}/content
   ↓
S3-compatible object storage
   ↓
encrypted binary bytes

For local development and local Kubernetes, the approved implementation uses MinIO.

The object storage contains ciphertext only:

Client encryption
       ↓
Gateway
       ↓
Files Service
       ↓
Object storage

Neither Gateway nor Files Service decrypts the file.

6. Recommended physical indexes

The approved data model explicitly defines the tables and primary keys, but does not provide a detailed PostgreSQL index section equivalent to the Auth section. Therefore, to avoid silently inventing unapproved indexes, I would keep the MPD's authoritative index definition to the approved primary keys:

files
PRIMARY KEY (file_id)

upload_sessions
PRIMARY KEY (upload_id)

upload_chunks
PRIMARY KEY (upload_id, chunk_index)

outbox_events
PRIMARY KEY (event_id)

That is the safest interpretation of the approved source.

Files Service MPD summary
PostgreSQL
│
├── files
│      Canonical FileId + lifecycle + operational metadata
│
├── upload_sessions
│      Durable resumable upload state
│
├── upload_chunks
│      Completed encrypted chunk metadata
│
└── outbox_events
       Transactionally committed domain events

S3-compatible object storage
└── files/{FileId}/content
       Encrypted binary object only
