# SC-015 — Validate Distributed Development Environment

## Executive Summary & Objectives

Card **SC-015** executes the comprehensive integration and validation of the SecureCloud distributed development environment under Milestone **M1: Buildable Distributed Skeleton**.

The primary objective is to prove empirically that a developer can obtain a clean SecureCloud checkout, build the project across supported toolchains, start the complete distributed development infrastructure, verify service health and readiness over mutual TLS (mTLS), verify persistence and data retention across non-destructive container recreation, observe resilience during simulated dependency outages, and shut down cleanly—all while strictly preserving the integrity of the developer workstation's existing services (most notably host PostgreSQL 14).

> [!IMPORTANT]
> **Frozen Architectural Scope & Constraints**:
> 1. **No Business RPC Inventions**: SC-015 validates the runtime infrastructure, health endpoints, transport probing, and mTLS security boundaries established by SC-001 through SC-014. It does **not** invent mock business RPCs (e.g. messaging delivery, user login flows, or file uploads) that belong to Milestone M2+.
> 2. **Observational Host PostgreSQL 14 Guard**: The developer host runs an active **PostgreSQL 14** instance on `localhost:5432`. SecureCloud workflows MUST NEVER attempt to stop, restart, reconfigure, or bind to host port `5432`. SecureCloud's containerized PostgreSQL 17 binds strictly to `127.0.0.1:5433`. The guard is **purely observational**.
> 3. **Non-Destructive Recreation vs Destructive Wipe**: SC-015 proves that persistence data survives standard container stop, restart, and recreation (`docker compose restart` / `docker compose up -d`). Destructive volume wipes (`docker compose down -v`) are strictly isolated and documented as destructive resets.
> 4. **Separation of Specification and Evidence**: This document (`specs/phase0/SC-015-tickets.md`) is the formal requirements and validation specification. Empirical execution results, logs, and audit records will be generated by ticket T06 into `docs/implementation/SC-015-evidence-dossier.md`.

### SC-015-T01 — Thin Distributed Lifecycle Orchestrator & Observational PG14 Guard

- **Status**: `[COMPLETE]`
- **Objective**: Provide a clean, dedicated orchestrator (`scripts/verify-distributed-dev.py` and wrapper `scripts/verify-distributed-dev.sh`) that sequences the 9-phase development environment lifecycle by delegating to existing SC-009–SC-014 validators, paired with a non-intrusive, purely observational host PostgreSQL 14 guard.
- **Why Required**: Developers require a single, deterministic command to orchestrate the lifecycle without manually executing multiple disparate shell scripts or duplicating verification logic.
- **Exact Files / Directories Affected**:
  - `[NEW] scripts/verify-distributed-dev.py`
  - `[NEW] scripts/verify-distributed-dev.sh`
  - `[MODIFY] scripts/verify-local.py` (add optional hook to invoke distributed runner)
- **Existing Implementation to Reuse**:
  - Reuses `scripts/verify-dev-pki.sh`, `scripts/verify-persistence-infra.sh`, `scripts/verify-health-endpoints.sh`, and `CMakePresets.json`.
  - Reuses `scripts/verify-local.py` ANSI color and stage result structures.
- **Dependencies**: SC-008, SC-011, SC-013, SC-014.
- **Implementation Approach**:
  1. **Observational Host PostgreSQL 14 Guard**:
     - Implement a non-intrusive socket observation using `socket.create_connection(("127.0.0.1", 5432), timeout=0.5)`.
     - *Hard Invariant*: Never attempt to stop, restart, kill, reconfigure, or remediate port 5432. If unavailable, warn or abort gracefully.
     - Inspect Docker host port bindings across ALL Compose services (`docker compose port <service> <port>`) and verify that:
       - No Compose container binds to host port `5432`.
       - Container `postgres` port 5432 maps strictly to host port `5433` (`127.0.0.1:5433`).
       - All exposed ports bind strictly to loopback (`127.0.0.1`), never `0.0.0.0`.
  2. **Thin Lifecycle Orchestration (Phases A through I)**:
     - Phase A (Clean State): Pre-flight check for port availability and running containers.
     - Phase B (Build): Execute native configure, build, contract check, and CTest suite.
     - Phase C (Infrastructure): Generate dev-pki (`generate-dev-pki.sh`) and start persistence stack.
     - Phase D (Services): Start 5 microservice containers and poll container health.
     - Phase E (Security): Delegate to `scripts/verify-health-endpoints.sh` and `verify-dev-pki.sh`.
     - Phase F (Persistence): Delegate to `scripts/verify-persistence-infra.sh`.
     - Phase G (Restart/Recovery): Validate container restart without volume loss.
     - Phase H (Teardown): Clean non-destructive stop (`docker compose down`).
     - Phase I (Recreation): Re-up stack and verify data retention.
- **Security Considerations**:
  - Mask all database passwords and credentials in console output.
  - Assert that all external port bindings are strictly bound to loopback `127.0.0.1`.
- **Test / Validation Strategy**:
  - Execute `python3 scripts/verify-distributed-dev.py` on the development workstation with host PostgreSQL 14 running.
  - Verify zero collisions, zero downtime for host PostgreSQL 14, and 100% exit code 0 across all delegated stages.
- **Acceptance Criteria**:
  - Orchestrator delegates strictly to existing validators without duplicating logic.
  - Host PostgreSQL 14 is confirmed healthy before, during, and after execution.
  - All 10 exposed service ports are verified to bind strictly to `127.0.0.1`.
- **Expected Evidence**:
  - Orchestration stage execution log with timings and exit codes.
  - Docker port binding inspection JSON.
- **Risks / Blockers**:
  - Docker Desktop daemon must be running on host.
- **Regression Protection**:
  - Existing `scripts/verify-local.py` default options (`--preset`, `--skip-*`, `--tidy`, `--full`) must remain completely untouched and pass identically.

### SC-015-T03 — Microservice mTLS & Direct Probe Validation

- **Status**: `[COMPLETE]`
- **Objective**: Validate that all 5 microservices enforce mutual TLS, accept valid service certificates with matching SAN DNS identities, and fail closed when presented with missing, invalid, untrusted, or plaintext connections.
- **Why Required**: Validates ADR-004, ADR-008, SC-009, and SC-010 in the integrated container environment.
- **Exact Files / Directories Affected**:
  - `scripts/verify-health-endpoints.sh`
  - `tests/integration/health_probe_cli.cpp`
- **Existing Implementation to Reuse**:
  - Dedicated CLI tool `securecloud_health_probe` (SC-013-T06).
  - Dev PKI verification in `scripts/verify-dev-pki.sh`.
- **Dependencies**: SC-009, SC-010, SC-013, SC-015-T01.
- **Implementation Approach**:
  1. **Strict Scope Limitation**:
     - Validate direct health/readiness probes over mTLS (`securecloud_health_probe` -> service).
     - Do NOT claim full service-to-service business communication is validated, as application RPCs do not yet exist.
     - Validate implemented identity checks: verify peer certificate SAN matches expected service DNS name (`extract_peer_service_identity()`).
     - Do NOT introduce hypothetical authorization assumptions (e.g. "Audit cannot call Auth") that have no implementation in the code.
  2. **Direct mTLS Health Probes (Positive Checks)**:
     - Probe `gateway` (port 50051, SAN `DNS:gateway`).
     - Probe `auth` (port 50052, SAN `DNS:auth`).
     - Probe `messaging` (port 50053, SAN `DNS:messaging`).
     - Probe `files` (port 50054, SAN `DNS:files`).
     - Probe `audit` (port 50055, SAN `DNS:audit`).
     - All probes must succeed and return `SERVING`.
  3. **Security Boundary Checks (Negative Checks)**:
     - Plaintext probe against mTLS listener: must fail closed (connection aborted / handshake failure).
     - Untrusted Root CA probe: must fail closed (`UNAVAILABLE` / certificate verify failed).
     - Missing client certificate: must fail closed (peer unauthenticated).
     - Server SAN mismatch: must fail closed (SSL target name override mismatch).
- **Security Considerations**:
  - Proves that no service exposes an unencrypted plaintext backdoor.
  - Proves mutual authentication is strictly enforced on all incoming connections.
- **Test / Validation Strategy**:
  - Execute positive and negative test cases using `securecloud_health_probe`.
- **Acceptance Criteria**:
  - All 5 services pass authorized mTLS health probes.
  - All negative security probes fail closed with non-zero exit codes.
  - No business RPC capabilities are claimed or fabricated.
- **Expected Evidence**:
  - Probe execution logs recording return codes and diagnostic outputs.
- **Risks / Blockers**: None.
- **Regression Protection**:
  - All 81 unit and integration tests continue to pass without modification.

### SC-015-T04 — Failure Modes, Outage Degradation & Recovery Validation

- **Status**: `[COMPLETE]`
- **Objective**: Validate microservice readiness degradation and automatic recovery during dependency outages, strictly derived from actual SC-013 dependency bindings, preserving the 250 ms transport probe bounded timeout.
- **Why Required**: Validates ADR-009 (Distributed Failure & Resilience) and SC-013 health semantics in a live containerized environment.
- **Exact Files / Directories Affected**:
  - `scripts/verify-health-endpoints.sh`
- **Existing Implementation to Reuse**:
  - Outage and recovery test in `scripts/verify-health-endpoints.sh` (Sections 4 & 5).
  - Non-blocking 250 ms TCP probe in `src/common/src/health/transport_probe.cpp`.
- **Dependencies**: SC-013, SC-015-T01.
- **Implementation Approach**:
  1. **Actual Dependency Bindings (Derived directly from `src/*/main.cpp`)**:
     - `auth`: readiness evaluator probes `config.db_host, config.db_port` (PostgreSQL 17).
     - `files`: readiness evaluator probes `config.db_host, config.db_port` AND `config.s3_endpoint` (PostgreSQL 17 and MinIO).
     - `messaging`: readiness evaluator probes `config.scylla_host, config.scylla_port` (ScyllaDB 6.0).
     - `audit`: readiness evaluator probes `config.db_host, config.db_port` (ClickHouse 24.8).
     - `gateway`: static ready (or probes configured peer).
  2. **Simulated Outage & Readiness Degradation**:
     - With all services running, stop container `postgres` (`docker compose stop postgres`).
     - Probe `auth` and `files` readiness: must degrade to `NOT_SERVING` because their evaluators detect TCP connect failure.
     - Probe `auth` and `files` liveness: must remain `SERVING` (process is alive and running).
     - Probe `messaging` and `audit` readiness: must remain `SERVING` (independent failure domains; ScyllaDB and ClickHouse remain healthy).
  3. **Dependency Restoration & Recovery**:
     - Restart container `postgres` (`docker compose start postgres`).
     - Wait for `postgres` container health check.
     - Probe `auth` and `files` readiness: must return to `SERVING`.
     - *Observation Window*: Use a bounded observation window (e.g. up to 10 seconds polling with 500 ms sleep) to observe convergence. This is an observation window for container state convergence, NOT an architectural microservice SLA.
  4. **Probe Timeout Preservation**:
     - Every probe evaluation strictly retains the `k_default_probe_timeout` of 250 ms. Never block or sleep inside probe logic.
- **Security Considerations**:
  - Services must fail closed: never return `SERVING` when persistence is unavailable.
- **Test / Validation Strategy**:
  - Automated stop, probe, restart, and probe cycle in `scripts/verify-health-endpoints.sh`.
- **Acceptance Criteria**:
  - Stopping `postgres` causes `auth` and `files` readiness to degrade to `NOT_SERVING` while liveness stays `SERVING`.
  - `messaging` and `audit` remain `SERVING`.
  - Starting `postgres` results in automatic return to `SERVING`.
  - 250 ms transport probe deadline is strictly preserved.
- **Expected Evidence**:
  - Timed health probe transition log showing degradation and recovery.
- **Risks / Blockers**: None.
- **Regression Protection**:
  - Preserves all SC-013 unit and integration test assertions.
