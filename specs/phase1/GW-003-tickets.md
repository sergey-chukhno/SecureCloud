## 1. Executive Summary & Architectural Scope

Card **GW-003** creates the SecureCloud API Gateway's reusable internal **gRPC client layer** for secure, low-latency inter-process communication (IPC) with backend microservices over mutual TLS (mTLS). 

The primary initial integration target is the **Authentication Service** (`securecloud-auth`), enabling the Gateway to perform session validation, token verification, and credential delegation. The architectural design must be strictly generalized to serve as the unified gRPC client foundation for subsequent microservices: **Messaging** (`GW-005`), **Files** (`GW-007`), and **Audit Logging** (`GW-008`).

               │              SecureCloud API Gateway                   │

### Key Invariants & Architectural Boundaries

1. **Strict Mutual TLS (mTLS) Transport Security (ADR-004, SC-010)**:
   - All internal gRPC channels must enforce cryptographic mutual authentication using X.509 certificates generated by the SecureCloud PKI (`deploy/dev-pki`).
   - The Gateway identifies itself strictly as `DNS:gateway`.
   - The Gateway validates the server certificate against the trusted Root CA (`ca.crt`) and strictly asserts the peer Subject Alternative Name (SAN), e.g., `DNS:auth`.
   - Cleartext HTTP/2 connections are strictly prohibited in all operational configurations.
2. **Strict No-Database Invariant (ADR-005, Gateway Design 3.1)**:
   - The Gateway owns **zero business data persistence**.
   - No database driver (`libpqxx`, `scylla`, `aws-sdk`, `clickhouse`) or backend business service implementation may be compiled, linked, or referenced by the Gateway.
3. **Observational Host PostgreSQL 14 Guard**:
   - Developer workstation host runs an active PostgreSQL 14 instance on `localhost:5432`. No Gateway test or client process may attempt to connect to, stop, or reconfigure port `5432`.
4. **Mandatory Bounded Deadlines & Cancellation (Gateway Design 3.24)**:
   - Every outgoing gRPC invocation must have an explicit deadline enforced via `grpc::ClientContext::set_deadline()`.
   - HTTP client disconnects or pipeline cancellations must propagate immediately to the backend via `grpc::ClientContext::TryCancel()`.
   - Unbounded waits or hanging RPC calls are strictly forbidden.
5. **Explicit Dependency Error Translation**:
   - Network dropouts, handshake errors, or backend outages must produce structured, typed dependency failures (`DependencyStatus::Unavailable`, `DependencyStatus::DeadlineExceeded`).
   - Internal infrastructure errors must never leak raw backend stack traces or internal topology to external consumers; errors must map cleanly into RFC 7807 Problem Details.
6. **M1 & M2 Non-Regression Invariant**:
   - All 169 existing unit and integration tests across Milestone 1 and Milestone 2 (GW-001, GW-002, SC-001 through SC-015) must continue passing cleanly with zero warnings (`-Wall -Wextra -Werror -Wpedantic`) across macOS AppleClang, Windows MSVC, and Windows MinGW-w64.

### GW-003-T02 — RPC Call Context, Deadline Enforcement & Cancellation Controller

1. **Ticket ID**: `GW-003-T02`
2. **Title**: RPC Call Context, Deadline Enforcement & Cancellation Controller
3. **Objective**: Implement a reusable `ClientCallContext` wrapper that manages `grpc::ClientContext` lifecycles, enforces deterministic call deadlines, supports cancellation propagation, and injects distributed tracing headers (`x-request-id`).
4. **Architectural Purpose**: Ensures all outgoing RPCs from the Gateway are bounded in execution time, preventing thread pool starvation and hung socket connections.
5. **Scope**:
   - Create `src/gateway/grpc/client_call_context.hpp` and `src/gateway/grpc/client_call_context.cpp`:
     - Class `ClientCallContext`:
       - Manages underlying `std::unique_ptr<::grpc::ClientContext>`.
       - Applies call timeout from `std::chrono::milliseconds` (configured or per-call override).
       - Injects `x-request-id` into outgoing gRPC metadata (`grpc::ClientContext::AddMetadata`).
       - Injects service identity and user-agent metadata.
       - Provides thread-safe `cancel()` triggering `grpc::ClientContext::TryCancel()`.
       - Queries `is_cancelled()`, `deadline_remaining()`, and `deadline_expired()`.
   - Unit tests in `tests/unit/gateway/client_call_context_test.cpp`.
6. **Explicit Out-of-Scope**: Global distributed tracing engines (OpenTelemetry integration owned by later monitoring cards).
7. **Dependencies**: Upstream GW-003-T01, GW-001. Downstream GW-003-T04.
8. **Exact Repository Starting Point**: `src/gateway/grpc/channel_manager.hpp`.
9. **Files/Directories to Create**:
   - `src/gateway/grpc/client_call_context.hpp`
   - `src/gateway/grpc/client_call_context.cpp`
   - `tests/unit/gateway/client_call_context_test.cpp`
10. **Files/Directories That May Be Modified**:
    - `src/gateway/CMakeLists.txt`
    - `tests/unit/CMakeLists.txt`
11. **Files/Directories That MUST NOT Be Modified**: `src/common/*`.
12. **Detailed Implementation Requirements**:
    - Default RPC deadline must default to `GatewayConfig::request_timeout_ms` (5000ms default).
    - `cancel()` must be `noexcept` and safe to invoke concurrently from HTTP connection teardown threads.
    - Custom metadata key constants must use lower-case conforming to HTTP/2 and gRPC specs (`x-request-id`, `x-client-service`).
13. **Testing Requirements**:
    - Verify deadline calculation: `context.deadline()` is set to `now() + timeout`.

### GW-003-T04 — Typed AuthServiceClient & Dependency Error Translation

1. **Ticket ID**: `GW-003-T04`
2. **Title**: Typed AuthServiceClient & Dependency Error Translation
3. **Objective**: Implement `AuthServiceClient` (and abstract interface `IAuthClient`) providing typed RPC invocations for the Gateway, mapping gRPC error statuses into structured Gateway `DependencyError` models.
4. **Architectural Purpose**: Decouples Gateway HTTP handlers and authentication middleware from raw gRPC stubs, enabling mockability in tests and unified error handling.
5. **Scope**:
   - Create `src/gateway/grpc/auth_client_interface.hpp`:
     - Abstract interface `IAuthClient` defining asynchronous and synchronous signatures for Auth operations:
       - `validate_session(const ValidateSessionRequest& req, const ClientCallContext& ctx)`
       - `authenticate(const AuthenticateRequest& req, const ClientCallContext& ctx)`

       - `revoke_session(const RevokeSessionRequest& req, const ClientCallContext& ctx)`

### GW-003-T05 — End-to-End Gateway-to-Auth mTLS gRPC Integration Test Suite

3. **Objective**: Implement comprehensive live end-to-end integration test `tests/integration/gateway_auth_grpc_integration_test.cpp` verifying live mTLS negotiation, SAN verification, deadline expiration, cancellation propagation, and failure handling between Gateway and an in-process Auth gRPC service.
4. **Architectural Purpose**: Proves that the Gateway gRPC client layer operates seamlessly and reliably over genuine network sockets with real PKI certificates before integrating authentication middleware in GW-004.
5. **Scope**:
   - Create `tests/integration/gateway_auth_grpc_integration_test.cpp`:
     - Spawns in-process mTLS gRPC test server listening on ephemeral port (`127.0.0.1:0`) presenting `deploy/dev-pki/services/auth/auth.crt` and `auth.key`.
     - Initializes Gateway `GrpcChannelManager` configured with `gateway.crt` and `gateway.key` targeting the test server with SAN `DNS:auth`.
     - Instantiates `AuthServiceClient`.
     - **Test Case 1 (mTLS Handshake & RPC Success)**:
       - Gateway invokes `ValidateSession`. Server returns valid response.
       - Confirms bidirectional certificate verification succeeds.
     - **Test Case 2 (Strict SAN Verification / Mismatch Rejection)**:
       - Channel configured expecting SAN `DNS:wrong_service`.
       - Handshake fails; RPC returns `UNAVAILABLE` / dependency error.
     - **Test Case 3 (Untrusted Client Certificate Rejection)**:
       - Client presenting untrusted/foreign certificate attempts call.
       - Server terminates handshake; call fails closed.
     - **Test Case 4 (Deadline Enforcement)**:
       - Server delays RPC execution past deadline (e.g. sleeps 500ms when timeout is 100ms).

     - **Test Case 6 (Server Outage & Reconnection)**:
       - Server is shut down while client is active.
